## 二、三个候选方向与打分

| 方向                                    | 复用既有资产                            | 两周内可验证                        | 需新建宿主 | 差异化说服力                                         | 合计      |
| --------------------------------------- | --------------------------------------- | ----------------------------------- | ---------- | ---------------------------------------------------- | --------- |
| **A · AI 游戏自动测试 Agent**（本项目） | **高** —— aiwarden 治理管道实测数字现成 | **能**（有具体被测对象 + 明确断言） | 不需要     | **强** —— 「治理组件 × 游戏」交叉点无人做（调研 §5） | **★★★★★** |
| B · AI NPC 引擎层                       | 中 —— 仅复用 `provider.ts` 抽象         | 需先造宿主                          | **需要**   | 需与成熟 NPC 竞品正面比较                            | ★★☆☆☆     |
| C · 作品集 landing page                 | 无                                      | 能                                  | 不需要     | 弱（纯门面）                                         | ★★☆☆☆     |

### 为什么选 A

1. **它是唯一能"站在自己已有资产上"的方向** —— aiwarden 的幂等键 / 版本 CAS / 租约独占 /
   检查点续跑 / 成本归因，都是**已实测过**的资产（aiwarden STATUS §2 有实测数字），
   接上游戏即可产生新价值；B 与 C 都要从零起。
2. **它补的是作品集里整类为零的方向** —— 06「AI 原生工具与 Agent」在 7 款游戏 + 15 个目录中
   完全没有对应物；而 03「故事与 AI NPC」需要一个宿主游戏，B 的交付物在宿主造出来之前是"零件"。
3. **调研明确该方向未挤爆且空位清晰**（调研 §6）—— 通过门 G1。

### 为什么暂不做 B、C

- **B（AI NPC）**：03 类目前**没有宿主游戏**，先做引擎层会得到一个无人使用的库。
  建议等 A 收口、有了稳定工程节奏后**连宿主一起立项**。
- **C（landing page）**：成本低但价值密度也低，随时可做，不占 P0。

## 三、项目定义

### 3.1 名称与定位

**名称**：`playtest-agent`
**定位**：**游戏的质量保障基础设施** —— 自主开局、按策略游玩、为每步产出治理证据、
产出可复现缺陷报告的自动化测试 Agent。

### 3.2 五条确定性承诺

> 产品第一屏就写这五条，而不是技术栈。
> 每条都必须有**可复现的验证命令 + 期望输出**（PRD §13 落地）。

| #      | 承诺                                                     | 验证方式                                                           | 状态                             |
| ------ | -------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------- |
| **P1** | Agent 无人值守自动完成一整局，产出完整可回放记录         | `npm run playtest -- --scenario smoke` → 完整 StepRecord 链 + 报告 | ✅ **已达成**（59 步 / passed）  |
| **P2** | 每个动作都有治理证据：幂等指纹 + 成本归因 + traceId      | 每步 StepRecord 含 fingerprint + tokens + traceId                  | ✅ **已达成**（内存替身链路）    |
| **P3** | 崩溃后续跑，**动作不重复生效**                           | 注入崩溃 → 续跑 → 副作用计数与基线逐项相等                         | ✅ **已达成**（集成测试）        |
| **P4** | 模型不可用时**降级到确定性基线**并继续跑完，报告显式标注 | 无端点时跑完 N 步且报告「降级说明」非空                            | ✅ **已达成**（60 步全标注降级） |
| **P5** | 发现真实缺陷时报告正确标红且**可复现**                   | 断言命中 → 报告标红 → 同 seed 重跑稳定复现                         | ⏳ **未达成** —— 见 §4.4         |

> **P5 的诚实状态**：实跑 41 个 seed、约 2400 步，游戏特异断言（OTH1–OTH7）**零违规**。
> othello 本身没有机制缺陷。过程中确实出现过一次"发现"，经查证是**本项目的断言误报**
> （通用 Oracle 无法区分 othello 的合法跳过与"该换没换"）—— 已修正断言分层。
> **这条误报比一个假缺陷更有价值**：它证明断言层本身在被真实数据检验。

### 3.3 反定位：我们明确不是什么

| 不是什么                        | 为什么                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------ |
| **不是取代 QA / 人工试玩**      | 调研 §4.1-5：AI playtesting agent 是"起点，不是完全验证过的 QA 替代品"；机器证不了"人看着不难受" |
| **不是性能测试 / 压测工具**     | 不测吞吐、不测延迟，只测**机制正确性**                                                           |
| **不是视觉回归工具**            | 走 HTTP API + 状态断言，不看像素。像素是噪声源，状态才是权威源                                   |
| **不是通用爬虫 / fuzzer**       | 动作来自**合法动作集**，不臆造越界输入；越界由契约测试单独覆盖                                   |
| **不改被测游戏**                | 既有游戏零改动（红线 2.2）                                                                       |
| **不追求"AI 棋力超过 minimax"** | 策略层的价值是**探索与复现**，不是下得更好                                                       |

## 四、差异化声明

### 4.1 「已有 TITAN / Razer QA Companion-AI / modl.ai / 公开 2048 实现，为什么还要这个？」

| 已有方案             | 缺什么                                                   | 本项目补什么                             |
| -------------------- | -------------------------------------------------------- | ---------------------------------------- |
| TITAN（MMORPG 研究） | 规模够不着；无成本数据                                   | 个人开发者可跑；**每步成本归因**         |
| 人机对照研究         | 是研究结论，不是可用工具                                 | 可复现的**工具 + 命令**                  |
| Razer / modl.ai      | 需付费；效果只有厂商自述；需每游戏定制训练               | 零成本；通用模型；**证据可查**           |
| 公开 2048 实现       | 只有架构，无治理层；不解析 DOM（本项目走 API，反而更准） | **幂等 / 成本 / trace / 崩溃续跑**这一层 |

**关键**：调研 §4.1-1 的结论 —— 「**用 AI 检视与解释；让确定性检查负责 pass/fail**」。
公开方案里，"确定性检查"是 Playwright 的截图与 ARIA 快照；
**本项目的"确定性检查"是游戏状态断言（Oracle）+ 幂等键**，比截图更准、更可复现。

### 4.2 一句话差异化

> **别人做"AI 帮你玩"，本项目做"AI 帮你玩，且每一步都留下可审计、可复现、不重复副作用的证据"。**

### 4.3 交叉验证：本项目的关键设计在别处的印证

| 本项目的设计                             | 外部印证                                                                               | 来源与证据等级                          |
| ---------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------- |
| 模型只做决策/表达，断言层裁决 pass/fail  | 「Use AI to inspect and explain; make deterministic checks responsible for pass/fail」 | 综述结论，**D**                         |
| 模型的输入只有合法动作集，越界即降级     | 「The model should not invent selectors or replace deterministic state checks」        | 综述结论，**D**                         |
| 观察→决策→动作→比对→报告 的循环          | Razer 描述的 gameplay agent 循环                                                       | 厂商文档，**B**                         |
| 每步成本归因                             | 全部来源**均未公布**单次运行成本与方差 → 这是真空                                      | 调研 §4.3-1，**D**                      |
| 幂等 / 崩溃续跑 / 租约独占               | aiwarden 自己的实测数字（删除生效 P95 1975ms、越权拦截 100%、断网重放工单数 1）        | aiwarden STATUS §2，**A**（本机自测）   |
| 断言层独立实现，不复用被测游戏的规则代码 | 「用游戏自己的规则校验游戏自己，会漏掉共模错误」                                       | 本项目自己的工程判断（ARCHITECTURE §5） |

## 五、这个项目不需要重新学的东西

| 资产                          | 位置                                               | 怎么用                                         |
| ----------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| aiwarden 治理管道             | 兄弟仓库 aiwarden（需自行检出）                    | **进程外消费**（HTTP / MCP），零改动           |
| aiwarden 的幂等键口径         | ADR-013 决策 6                                     | 冻结契约 ⑦ 与之同构                            |
| othello 的规则语义            | `othello-online/src/utils/gameLogic.ts`            | 被测对象；**特异断言独立重写**，不复用它的代码 |
| othello 的本地免云端 mock API | `othello-online/vite.config.ts` 的 `mockApiPlugin` | 被测游戏的启动方式（零 EdgeOne 依赖）          |
| 纯函数分层 + PRNG 自实现      | `tongshi-ju/lib/engine/*`                          | 本项目地基的分层约定                           |
| Node 内置测试运行器           | `node --import tsx --test`                         | 不引测试框架                                   |
| CI 两段结构                   | `tongshi-ju/.github/workflows/ci.yml`              | 本项目 CI 的写法                               |

**不需要重新学的**：Maven / Spring / PG / Redis / Kafka（治理面是 aiwarden 的事）、
Next.js 运行时（被测游戏是 Next.js，但本项目只发 HTTP 请求）、
视觉模型调参（不走像素路线）。
