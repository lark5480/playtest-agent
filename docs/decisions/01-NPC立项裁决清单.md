## 第一部分：定位与范围（1–6）

### 1. 宿主：通识局加"老师 NPC"，不新造游戏

**结论**：在 `tongshi-ju` 内新增 `lib/npc/`，作为**难度调节器**（记住薄弱域 → 据此选域与点评）。
**不新造叙事游戏，不做独立 NPC 框架库。**

**理由**：

- 灵感库 03 类的原文是「**让角色有记忆，让选择改变故事**」——
  这是**引擎能力**的要求，不是"要做一款新游戏类型"的要求；读成后者是过度解读；
- 通识局定位是"12 域知识闯关"，**"针对你薄弱域出题"本就是它最自然的下一步**，不是硬塞的功能；
- 调查确认 7 款游戏**无一有叙事载体**（README 提及"对话/剧情/角色/NPC/叙事"各 0–1 次，
  全仓 891 处 grep 命中全是 UI 层同名词）—— 新造游戏要把工作量从引擎层膨胀到完整游戏；
- 独立库没有宿主就是"零件"不是"作品"。

**放弃了什么**：放弃了"做一个完整的叙事游戏"这条更有传播性的路线。
也放弃了"先做通用 NPC 框架，将来接多个游戏"——那会让交付物脱离作品。

### 2. 作品集归属：游戏作品集，不进求职精选作品

**结论**：本项是《AI 游戏作品》灵感库 **03 类**的补位，**不进**求职精选作品集。

**理由**：

- 求职精选作品现已是全 Java 后端（chess-arena 已被 aiwarden 替换）；
- 内部旧盘点（2026-10-06）的约束 1「必须 Java 后端」其**前提已变**——
  它约束的是"**替换**精选作品位"，不是"**做游戏**"；
- 两套作品集**服务两种目的**（求职看工程深度与岗位匹配；游戏作品集看品类覆盖与产品感），
  技术栈约束强度不同（游戏是 TS，不该被后端求职的约束绑住）。

**放弃了什么**：放弃了"再做一个非 Java 后端项目去挤精选作品位"的冲动。

### 3. 约束 3 的落点：治理武器用在对话上

**结论**：差异化主张 = **「NPC 的每次对话都有可审计的成本与状态证据」**。
治理武器落在：**记忆按用户隔离 · 每次对话 token 入账 · 对话预算熔断 · 长对话续跑**。

**理由**：内部盘点约束 3「一致性 / 幂等 / 对账 / 故障注入是最稀缺的武器，
新项目应当在这个武器的新战场打」。调研同时确认（§6.1）：
**所有查到的来源均未涉及单次对话的成本归因 / 配额 / 续跑 / 审计**。

**放弃了什么**：放弃了"NPC 架构做得多先进"这条竞争轴 ——
调研已证明架构层（Generative Agents 三段检索）**已是公认蓝图，不构成差异化**。

### 4. NPC 是难度调节器，不是聊天机器人

**结论**：NPC **不接受自由聊天**。它的输出只有两类：**选域决策** 与 **点评**。
成功标准 N2 硬性要求「选域决策真的改变了每日题集」。

**理由**：风险 R1（NPC 沦为聊天挂件）是本项目**概率最高的失败模式** ——
一旦 NPC 只是陪聊，它对通识局没有任何价值，也补不上 03 类的"让选择改变故事"。
把它钉死在"影响玩法"上，是唯一有效的防线。

**放弃了什么**：放弃了"让玩家和 NPC 自由聊天"的趣味路线。

### 5. 只读既有引擎

**结论**：NPC **只读** `lib/engine/*` 与 `content/`，新增代码全部在 `lib/npc/`。
`lib/engine/*` **零改动**。

**理由**：通识局 `AGENTS.md` §2 四条红线（每日挑战必须无状态 / 服务端权威 /
凭证纪律 / 依赖克制）都是产品级约束，改引擎会波及既有玩法与测试。

**放弃了什么**：放弃了"在引擎里加一个 npcAware 选域参数"的捷径 ——
那会让纯函数引擎依赖 NPC 状态，直接破坏"每日挑战无状态"红线。

### 6. 与 aiwarden 的关系：可选增强，不作前提

**结论**：治理接入（成本归因 / 配额 / 续跑）**是可选增强**，不是立项前提。
MVP 先在本地完成"每次对话有成本记录"，**不依赖 aiwarden 在线**。

**理由**：

- aiwarden 侧**没有 NPC 相关工具**（实测注册的是 `assign_ticket` / `create_ticket`）；
- 本项目对 aiwarden **零改动**，注册 NPC 工具需另行协调；
- 且 aiwarden 是**后端治理组件**，通识局是**纯前端 + 本地存储**的游戏 ——
  让一个浏览器游戏去连 Java 治理服务，在架构上是错配的。

**放弃了什么**：放弃了"用 aiwarden 撑起 NPC 治理"的完整叙事。
改为：先把**本地可复现**的证据链做实（成本记录 + 幂等键 + 可复现断言），
治理服务接入作为后续增强。

## 第二部分：记忆模型（7–11）

### 7. 三层记忆，不用向量库

**结论**：

```
lib/npc/memory/
├─ facts/       结构化事实（必须）：每域掌握度 / 连续对错 / 偏好域
├─ episodes/    情景层（必须）：最近 N 次答题事件（时间戳 + 重要度）
└─ retrieve.ts  检索
```

**不用向量数据库、不做嵌入检索。**

**理由**：

- 调研 §5.1：通识局的"相关"是**结构化**的 —— "这题属于哪个域"是确定的，
  用嵌入反而引入外部依赖与不确定性；
- 依赖克制是通识局的红线之一（红线 2.4），引入向量库直接违反；
- 工程综述的四层里，向量层是"通用 NPC 场景"才需要的。

**放弃了什么**：放弃了通用 NPC 的完整四层（缓冲 + 摘要 + 向量 + 事实），
只保留**结构化事实 + 情景 + 检索**。

### 8. 检索评分：沿用 Generative Agents 的三段式

**结论**：

```
score = α_rec · recency + α_imp · importance + α_rel · relevance
```

recency 用指数衰减（论文 γ=0.995）；importance 由 LLM 打 1–10；
relevance 用**结构化匹配**（域/难度匹配）替代嵌入相似度；
三项各自归一到 [0,1] 后**等权相加**，取 top-k。

**理由**：这是**该论文最可复用的部分**（证据等级 A），
且被后续大量实现沿用（"reference design"）。

**放弃了什么**：放弃了 relevance 用嵌入余弦相似度 —— 通识局的域是离散且确定的。

### 9. importance 必须有规则化替身（降级路径）

**结论**：`importance` 有两个来源，**落在同一 [1,10] 标度**：

| 场景               | 来源                                                                |
| ------------------ | ------------------------------------------------------------------- |
| 有模型             | LLM 打分（遵循论文）                                                |
| **降级（无模型）** | **规则打分**：答错 > 首次答对新域 > 重复答对；连击 / 错题本状态加权 |

**理由**：论文的 importance 依赖 LLM，而通识局**已有 provider-null 降级约定**，
承诺 N3 要求"无模型也能玩"。若 importance 只有 LLM 来源，
降级路径就失去了"重要性"这一维，检索退化为只看近因。

**放弃了什么**：放弃了"论文原样"（论文不关心降级）。
代价是 importance 的语义在两条路径下不完全等价 —— 用同一标度缓解，但不能完全消除。

### 10. 检索必须有 topK 上限与最小阈值

**结论**：topK **2–4 条**（工程综述取值）；低于最小相关度的一律丢弃。

**理由**：调研 §7.1-4：「无关回忆浪费 token 且让角色混乱」。
通识局每次只出 5 题，注入太多记忆反而挤占 prompt 预算。

**放弃了什么**：放弃了"把相关记忆全塞进去"。

### 11. 反思机制不进 MVP

**结论**：反思（自问 → 检索 → 综合 → 写回）**列为后续项**。MVP 只做
**记忆流 + 检索 + 结构化事实**。

**理由**：调研 §5.3：反思是"让 NPC 更像人"的增强，而本项目的差异化在**治理证据**，
不在拟人度；且反思每次都调模型，成本与复杂度都上一个量级。

**放弃了什么**：放弃了"NPC 会产生高层洞见"的表现力。

## 第三部分：工程约定（12–15）

### 12. 核心决策纯函数化

**结论**：`lib/npc/` 的状态机、记忆存取、检索打分、意图分类**全部是纯函数**，
无 IO、无网络、不读时钟（时间由入参注入）。

**理由**：

- 与通识局 `lib/engine/*` 的既有约定一致（红线 2.4 的同源要求）；
- 与 playtest-agent 的 `src/core/` 同构 —— 同一套工程范式跨项目复用；
- 纯函数才能单测、能回放、能断言（承诺 N5 的前提）。

**放弃了什么**：放弃了"在 React hook 里直接调模型"的便捷写法。

### 13. LLM 只在两处介入

**结论**：LLM 只做 ① **意图分类**（把玩家的自由输入映射到意图枚举）② **台词生成**（点评措辞）。
**不裁决规则**（选域逻辑、掌握度更新、断言判定全部确定性）。

**理由**：沿用 playtest-agent 的外部印证 —— 「用 AI 检视与解释；让确定性检查负责 pass/fail」。
也符合调研对 importance 的处理（模型可参与，但不能是唯一来源）。

**放弃了什么**：放弃了"让模型自由决定出哪些域" —— 那会让每日挑战失去确定性
（通识局红线 2.1 要求每日挑战无状态、确定性）。

### 14. 出题可复现靠 PRNG，不靠模型

**结论**：NPC 的选域决策是**确定性的**（种子化 PRNG + 记忆输入），
LLM 只在"点评说什么"上发挥作用。

**理由**：通识局的每日挑战必须**确定性**（红线 2.1：题集由「日期 + 领域集合」的纯函数确定）。
若选域受模型影响，同一天不同人拿到不同题集，红榜与 PK 都无法成立。

**放弃了什么**：放弃了"让模型挑最合适的题"这种听起来更聪明的做法 ——
它与"每日挑战必须无状态、确定性"直接冲突。

### 15. 记忆按用户隔离

**结论**：NPC 记忆**按用户身份分区存储**（本地存储 key 区分），互不可见。

**理由**：

- 通识局是纯前端 + localStorage，天然单机 —— 但**同一浏览器多人使用**（家庭共用电脑、
  演示场景）会串味；
- 这是治理武器（多租户隔离）在游戏侧的最小落地。

**放弃了什么**：放弃了"本地不做隔离，靠用户自觉"的省事做法。

## 第四部分：待拍死项（16–18）

### 16. 未决：importance 的规则权重

**结论**：**待实现时标定**。规则打分先按「答错 = 10 / 首次答对新域 = 6 / 重复答对 = 3」起步，
用真实的答题事件分布校准。

**理由**：调研已标注「γ=0.995 是否适合『每天 5 题』的节奏」为待验证 ——
论文是小游戏沙盒，通识局是每天 5 题，节奏差异很大，照搬常数不合理。

**放弃了什么**：放弃了"直接用论文参数"（那是没有依据的照抄）。

### 17. 未决：NPC 的出题自由度

**结论**：NPC 可以在**固定 12 域内**调整选域权重，
但**不能改变"本命域 + 2 个盲盒"这个结构**（盲盒是每日轮转、全网一致的机制）。

**理由**：盲盒轮转是通识局的核心公平性设计（"当天全网一致"），
NPC 若能改它，会破坏 PK 的可比性。

**放弃了什么**：放弃了"NPC 可以推荐第 4 个域"这类自由度。

### 18. 未决：是否接入 aiwarden 做治理

**结论**：**MVP 不接**，作为后续增强。理由见裁决 6。

**什么时候拍死**：MVP 完成、且通识局确实出现"多用户 / 长会话 / 成本可见"的需求时。
