## 第一部分：立项与形态（1–10）

### 1. 定位：游戏的质量保障基础设施

**结论**：本项目是**工具**，不是游戏，也不是平台。

**理由**：

- 它被测的是**另一个仓库里的游戏**（红线 2.2 既有游戏零改动）——同仓库放游戏会破坏那条红线；
- 灵感库的「06 AI 原生工具与 Agent」需要的正是**工具类**作品；
- 工具的验收标准是**可复现的命令**，不是"好玩"。

**放弃了什么**：放弃了"把 Agent 做成一个能给人玩的游戏"的路线（那样做更有传播性，
但会与「自动测试」的核心价值冲突，且拿不到幂等/续跑这类硬证据）。

### 2. 优先补 06 类而非 03 类（AI NPC）

**结论**：先做 06（AI 原生工具与 Agent），03（故事与 AI NPC）留候选池。

**理由**：

- 06 有**现成可复用的资产**（aiwarden 的治理管道，实测数字现成）；03 没有宿主游戏；
- 调研确认 06 方向未挤爆且空位清晰（[调研 §6](../research/2026-11-03-竞品与自动测试现状.md)）；
- 03 的交付物在宿主造出来之前是"零件"不是"作品"。

**放弃了什么**：放弃了"同时做两个"——并行会摊薄深度，而本项目最缺的是深度不是广度。

### 3. 技术栈：TypeScript

**结论**：TypeScript 5.5，Node 24，运行时零依赖。

**理由**：

- 被测游戏全是 TS（othello / chess-arena / tongshi-ju），可直接 import 引擎；
- 既有 CI 习惯是 `node --import tsx --test`（tongshi-ju / chess-arena）——不引测试框架；
- 治理面（Java）在进程外，走 HTTP/MCP，**不需要跨语言共享代码**。

**放弃了什么**：放弃了 Java —— 那样能直接复用 aiwarden 的 Java 模块，
但要拖进 PG+pgvector+Redis+Kafka 全家桶，且用不上 TS 侧的引擎。

### 4. 仓库形态：独立仓库

**结论**：独立仓库（本仓库），与作品集其余 15 个项目平级。

**理由**：既有 15 个项目各自独立（独立 CI 徽章 / MIT / README），
新项目混进既有仓库会破坏"一个项目一个仓库"的浏览结构，也拿不到独立的 CI 徽章。

**放弃了什么**：放弃了"作为 aiwarden 的子模块"——那会污染 aiwarden 的公开版定位
（STATUS §5 对公开范围有严格约定）。

### 5. aiwarden 零改动

**结论**：只消费 aiwarden 的既有边界（`POST /api/v1/agent/tools/{tool}/invoke`、
`/api/v1/agent/runs/{sessionKey}/resume`），**不修改它一个字节**。

**理由**：

- `AgentDagEngine` 是**固定 10 节点单次问答管线**（`AgentRunContext` 硬绑 `ChatAskRequest`，
  ADR-013 决策 1），本项目需要的是**循环** —— 形状不同，强行套用会污染 aiwarden 已收口的 M4 口径；
- aiwarden STATUS §4 明确「若继续，先补可验证性、再扩范围」；
- 治理管道本身与业务域无关（`ToolInvocationService` grep `ticket` **零命中**）→ 进程外复用是干净的。

**放弃了什么**：放弃了"给 aiwarden 加一个游戏 Agent 模块"——那需要改动它的公开版契约与 ADR 链。

### 6. 既有游戏零改动

**结论**：被测对象只读。首个适配器打 othello-online 的本地 `preview`，
**零改动**（其 `vite.config.ts` 的 `mockApiPlugin` 已提供内存版 `/api`）。

**理由**：

- othello-online 本地 mock API 与 Edge Functions **响应形状一致**，无需改任何一行；
- 通用原则：Agent 走**黑盒 HTTP**，更接近"真实用户"的真相，且能测到接口层问题
  （409 冲突、乐观并发）——进程内 import 测不到这些。

**放弃了什么**：放弃了"给 chess-arena 加 `legal-moves` 只读接口"的方案（延后到后续 1）。
该接口能让 Agent 不用试错非法走子，但属于改既有游戏，与红线冲突，故延后。

### 7. 零云端审批依赖

**结论**：P0 不引入任何需人工审批的外部资源作为关键路径。
被测游戏跑本地进程；EdgeOne KV 审批不通过**不影响任何验收项**。

**理由**：实测确认 othello-online 的 `vite.config.ts` 有 `mockApiPlugin`
（`configureServer` + `configurePreviewServer` 双向挂载），注释原文：
「使本地无需 EdgeOne / KV 即可用两个浏览器窗口验证完整对局」。

**放弃了什么**：放弃了"部署到公网供外部人试玩"这条验证路径（EdgeOne KV 审批未通过）。
隧道能力本机已有（三个仓库内置 `cloudflared.exe`），但那是增强项不是依赖。

### 8. 合法动作集由适配器独立计算

**结论**：适配器**不复用被测游戏的规则代码**，独立重写合法着法计算。

**理由**：用游戏自己的规则校验游戏自己，会漏掉**共模错误** ——
双方共享同一个错误假设时，校验必然通过。本项目的特异断言（OTH1–OTH7）全部独立实现。

**放弃了什么**：放弃了"直接 import `gameLogic.ts`"的省事做法（也省掉了跨仓库依赖）。

### 9. 断言分层：通用 vs 游戏特异

**结论**：通用层只判**通用可判**的；回合跳过规则由**游戏特异**断言负责。

**理由**（这条是被真实数据逼出来的）：

- 实测误报：seed=123 报 `G1-turn-did-not-alternate`，查证后确认是 **othello 的合法跳过**
  （`gameLogic.ts:296-303`：对方无子可下 → 保持当前回合）；
- 根因：`legalActions` 永远属于**当前执子方**，于是"合法跳过"与"该换没换"在通用层**形状完全相同**，
  **无法区分**；
- 修正：通用层只保留"回合切换后新执子方须有合法动作"；跳过规则交给 OTH6。

**放弃了什么**：放弃了通用层"回合必须交替"这条断言 —— 硬判就是误报，
而误报会让整个报告失去可信度。

### 10. 决策确定性：PRNG 按 seed 缓存实例

> **修订**：本条已被裁决 27 取代——PRNG 改为按 `(seed, observation.seq)` 无状态派生；
> 标题与结论保留为当时记录。当前口径见 [`docs/TESTING.md`](../TESTING.md) §6。

**结论**：策略的 PRNG **按 seed 缓存实例**，不掺局面内容、不掺房间号。

**理由**（同样是实测逼出来的）：

- 原实现把 `hashPosition(局面)` 混进种子 → 局面里含房间号 → 每次开新局房间号都不同
  → **同 seed 的两次运行动作序列不同** → 违反红线 2.4，缺陷无法复现；
- PRNG 有状态：每次新建则每步都取序列第一个数 → 探索性为零；
- 按 seed 缓存 → 同 seed 整局序列确定。

**放弃了什么**：放弃了"掺局面内容以增强多样性"的原设计 —— 多样性可以用多 seed 扫描获得，
不值得牺牲确定性。

## 第二部分：治理与证据（11–14）

### 11. 幂等键含动作内容摘要（不只是 businessKey + session + stepNo）

**结论**：键 = `businessKey :: session :: stepNo :: digest`，
`digest = sha256(canonicalize({ stepNo, payload }))`。

**理由**：

- **stepNo 必须参与摘要**：否则"第 3 步与第 7 步做了同一个动作"会撞键，
  续跑时误判为重放而**跳过真实动作**（单测阶段抓到并修正）；
- **动作内容必须参与**：原实现的键不含内容 → "同一步的不同动作"被误判为重放而**漏执行**
  （契约测试阶段抓到并修正，现由契约用例锁死）。

**放弃了什么**：放弃了"键只含三段"的简化 —— 简化会换来漏动作或跳过动作的真 bug。

### 12. 替身与真实实现跑同一套契约测试

**结论**：`InMemoryGovernanceClient` 与 `AiwardenHttpClient` **必须**跑同一套治理契约测试。

**理由**：这是 aiwarden AGENTS §4 点名的坑形态 —— **不报错、只是静默不生效**。
若替身与真实实现行为不一致，就会出现"单测全绿但真实链路是坏的"。

**放弃了什么**：没有放弃任何东西 —— 这是**加**了一条约束。当前代价是：
真实链路的 8 条契约在本机**跳过**（Docker 不可用），缺口如实记录在 ARCHITECTURE §6。

### 13. 不静默降级

**结论**：模型不可用 → `degraded: true` + `degradedReason`，**显式写进报告**；
治理面不可达 → 报告标注 `governanceSource: in-memory` 与降级原因。

**理由**：承诺 P4 的价值恰恰在于"**如实标注**"。悄悄换个策略假装无事发生，
等于报告里的降级信息是假的 —— 而那正是这条承诺要证明的东西。

**放弃了什么**：放弃了"降级路径不写报告"的省事做法。

### 14. 集成测试跳过而非伪装通过

**结论**：被测游戏不可用 / aiwarden 不可达时，相关集成用例**跳过并打印原因**，
**不允许**改断言让它"通过"。

**理由**：本项目的核心价值是**证据可信**。一个"跳过即通过"的门禁会让 CI 绿灯失去意义
（这正是 aiwarden AGENTS §4 的坑）。

**放弃了什么**：放弃了"CI 必须全绿才算数"的严格要求 —— 改为"**跳过必须带原因**"。

## 第三部分：范围与边界（15–18）

### 15. MVP 不含多游戏并行

**结论**：MVP 只做 othello-online 一个适配器；chess-arena 适配器延后。

**理由**：适配器契约（7 条用例）已把"接第二个游戏"的成本降到最低，
但**先证明一个适配器跑通**比同时做两个更稳。

**放弃了什么**：放弃了"一次做出通用多游戏框架"的诱惑。

### 16. MVP 不含场景级预算熔断

> **修订**：本条的暂缓决定已被裁决 33 取代 —— 请求前预扣硬调用次数 + usage 软停止线
> 已实现（PRD §14 后续 2 完成）。

**结论**：每步的 tokens 已在采集，但**熔断阈值**留到后续。

**理由**：本机无模型端点（无 Key），熔断阈值无法用真实成本标定 ——
**拍一个没有依据的阈值不如不拍**。调研也确认无人公布单次运行成本（调研 §4.3-1）。

**放弃了什么**：放弃了"现在就加一个拍脑袋的 token 上限"。这是有意识的推迟，
不是遗漏（PRD §16 未决 U4 已记录）。

### 17. 不走像素 / 视觉回归路线

**结论**：走 HTTP API + 状态断言，不看像素。

**理由**：

- 调研结论：**像素比对有噪声**，ARIA 快照稳定但语义有限；视觉模型**约 1/8 场景描述是错的**；
- 游戏状态是权威源 —— othello 的 board / moveCount / updatedAt 是精确的，像素不是；
- 走 API 还能测到 HTTP 层的问题（409 冲突、乐观并发）—— 本项目已实测有效。

**放弃了什么**：放弃了"支持 canvas 渲染游戏"这个更大的游戏集合 —— 但那类游戏
本来就需要改游戏加 `data-testid` 钩子，与红线 2.2 冲突。

### 18. P5「发现真实缺陷」允许未达成

**结论**：MVP 的完成判定**不强制**要求发现真实缺陷；但必须**如实记录**扫描结论。

**理由**：

- 实测扫描 41 个 seed、约 2400 步，游戏特异断言**零违规** —— othello 本身没有机制缺陷，
  这是**真实结论**，不是没做；
- 过程中的一次"发现"经查证是**本项目的断言误报**（裁决 9），修正后归零；
- **伪造一个缺陷来满足验收标准，是本项目最该避免的事** —— 那会毁掉"证据可信"这个核心资产。

**放弃了什么**：放弃了"至少交一个 bug"这条原始验收要求。替代口径：
**价值锚点从"找 bug"改为"证据链 + 并发场景 + 可复现"**，且并发场景已实测出
「乐观并发保护有效」这一有价值的结论。

## 第四部分：执行顺序（19）

### 19. 执行顺序：地基先行，文档补齐收口

**结论**：实际执行顺序为 **Stage 0（地基）→ Stage 4–6（实现与验收）→ Stage 1–3（文档补齐）**。

**理由**：

- 地基的 8 项冻结契约需要在**真实代码跑起来**之后才能确认定得对 ——
  本次就有两条在实现中被发现需要调整（裁决 11 的键构成、裁决 9 的断言分层）；
- 但**收口条件不变**：Stage 1–3 的文档必须在 Stage 6 验收**之前**补齐并经评审，
  否则不得视为本项目收口（[立项 §6](../research/2026-11-03-选题论证与差异化声明.md) 已如实记录该时序）。

**放弃了什么**：放弃了"严格先文档后实现"的常规顺序 —— 在这个项目里，
地基的**形状**只有跑起来才说得清；文档的价值在于是**记录已验证的结论**，不是预言。

## 第五部分：真实链路与证据收口（20–29）

> **背景**：2026-11-04 本机 Docker 恢复可用，真实 aiwarden 链路首次实跑。
> 实跑暴露了三个**只有真实实现才会暴露**的缺陷（内存替身全都测不出来）。

### 20. 租户标识必须是数值字符串

**结论**：`X-Aiwarden-Tenant-Id` 的值必须是**数值字符串**（默认 `"1"`，对应种子数据
`id=1, name=demo-tenant`），**不能**用 `"playtest"` 这类语义化字符串。

**理由**：aiwarden 的 `tenant_id` 是 `long` —— `TenantContext.requireTenantIdAsLong()`
对非数值直接拒绝，HTTP 400「租户标识不是合法数值，拒绝执行」。
这不是"格式偏好"，是**类型约束**；用字符串会让每一次调用都被拒。

**放弃了什么**：放弃了"用可读租户名"的便利。语义信息移到 `userId` 头（那里是字符串）。

### 21. 下游唯一约束字段必须承载**全部**幂等维度

**结论**：客户端传给 `create_ticket` 的 `orderRef` 必须是**完整幂等键**
（`businessKey:session:stepNo:digest`），**不能**只传 `digest`。

**理由**（实测踩到）：本项目冻结契约 ③ 的 `digest` **只吃 `{stepNo, payload}`** ——
它是"动作身份"，刻意不含 businessKey/session。但 `create_ticket` 用 `orderRef` 做
唯一约束（`uk_ticket_tenant_idem`），于是：

> **不同 session 的同一动作** → 同一个 `digest` → 同一个 `orderRef`
> → `ON CONFLICT DO NOTHING` → **副作用静默丢失**（看起来"成功"，实际没发生）。

**关键区分**：`digest`（动作身份）与 `orderRef`（完整幂等键）是**两个层次的键**，
下游系统的唯一约束字段必须用后者。把"内容摘要"直接当"业务唯一键"是典型的层次混淆。

**放弃了什么**：放弃了"`digest` 加上全部维度更省事"的写法 ——
那会让冻结契约 ③ 的语义（动作身份）变浑浊。改为**两个键各司其职**。

> **修订（裁决 28）**：分隔符统一为 `::`，幂等维度不变。

### 22. 动作内容的规范化必须在本侧完成

**结论**：写入工具输入的动作内容必须先经 `canonicalize`（键序无关），
**不能**指望服务端排序。

**理由**（实测踩到）：aiwarden 侧用 `ORDER_MAP_ENTRIES_BY_KEYS` 序列化，
但那只保证**顶层** Map 有序 —— **嵌套结构不保证**。
客户端原本把 `JSON.stringify(action)` 原样写进 `title`，
于是 `{row, col}` 与 `{col, row}` 产生不同 title → 不同 idemKey
→ 治理面认不出这是同一个动作 → 幂等失效。

**放弃了什么**：放弃了"服务端会帮我排序"的假设。

### 23. 真实实现不具备的能力，标「不适用」而非删断言

**结论**：治理契约中「单次工具调用返回 traceId」一条标记 `inMemoryOnly: true`，
对真实实现**显式跳过并注明原因**（`（不适用：真实实现不具备该能力）`）。

**理由**：真实 aiwarden 的 `ToolInvokeResponse` **没有** traceId 字段 ——
traceId 属于 session 层（`t_agent_session.trace_id`）。
但"这条不适用"与"这条通过"是**两回事**，必须让报告能区分：
删断言会让真实链路的通过数虚高；改成"通过"则是撒谎。

**放弃了什么**：放弃了"8/8 全绿"这个更好看的数字。真实链路是 **7 实跑 + 1 不适用**。

### 24. 报告只增可选字段：traceId / 成本 / 来源口径

> **修订**：本条「`schemaVersion` 仍为 `1`」的限制已被裁决 30 取代 —— 报告升级 v2，
> 旧 v1 不补造。字段扩展的历史记录保留。

**结论**：契约 ⑧ 的 `ReportJson` 增加**可选**字段：`steps[].traceId`、
`steps[].llmTokens`、`steps[].governanceTokens`、`steps[].tokenSources`、
`steps[].tokensUnavailableReason`，以及顶层 `usage` 汇总。`schemaVersion` 仍为 `1`。

**理由**：README 早就宣称「每步带成本归因 / traceId」，但报告产物把它们丢了 ——
证据只在内存对象里，等于无法自证。只增可选字段是向后兼容的扩展，不改变既有语义。

**放弃了什么**：放弃了为了「字段整齐」把 `schemaVersion` 升到 2 ——
升版会让既有解析器无谓地拒绝旧报告，而新增字段本身不影响旧解析器。

### 25. 成本来源必须分开记账，拿不到就标 unavailable

**结论**：模型 token 与治理 token **不合账**：

- `model-usage`：模型响应的 `usage`（真实 token）；
- `governance-usage`：aiwarden 工具调用的配额当量（默认 100/次，**不是**模型 token）；
- `synthetic`：内存替身的固定值，报告必须注明「不代表真实成本」；
- `unavailable`：本应可归因但未取得，**不填 0**，并写明原因。

**理由**：把两种口径加成一个「total」会制造看似精确实则失真的成本数字；
把缺失填 0 会让「没有数据」伪装成「成本为零」。二者都会毁掉报告的可信度。

**放弃了什么**：放弃了「一个 total 走天下」的简洁展示。报告必须先说清来源，再给合计。

### 26. 续跑用检查点 + pending 意图；恢复不了就失败

**结论**：

- 检查点落 `reports/checkpoints/`（gitignore），含 token 但不进日志/报告；
- 每步**执行前**写 pending（action + beforeHash + `projectAfter` 的 expectedAfterHash），
  执行后再写 committed；
- 恢复时用状态哈希三分支：等于 expectedAfter → 记 `replayed` 不重复执行；
  等于 before → 用**同一个 action/fingerprint** 重做；两者都不是 → 显式失败；
- `adapter.resume(token)` 返回 null 时**显式失败**，不再静默新开一局。

**理由**：原实现只有库内 `resume`，CLI 无法续跑；测试自己承认续跑会新开一局，
`businessKey` 不同导致幂等键不命中。把「动作已生效、检查点未落」的窗口靠
「先写意图 + 状态哈希」判定，才能在不猜的前提下做到不重复副作用。

**放弃了什么**：放弃了「恢复失败就重建一局继续跑」的省事路径 ——
那会让报告看起来跑完了，实际换了一局，副作用与证据都对不上。

### 27. 续跑确定性用无状态 PRNG

**结论**：`HeuristicStrategy` 不再按 seed 缓存有状态 PRNG，改为每步
`createPrng(seedFrom(`${seed}:${observation.seq}`))`。

**理由**：有状态 PRNG 的序列依赖「从第 0 步一路走到这里」；新进程续跑时内部状态已丢，
从中间局面重新决策会得到不同动作，与「同 seed + 同局面 → 同动作」冲突。
按 `(seed, seq)` 派生后，决策只依赖显式输入，续跑与独立运行动作序列一致。

**放弃了什么**：放弃了现有 smoke/chess 的动作序列（无 golden 值，需重跑样例报告）。
换来的是一条能自洽解释的确定性红线。

### 28. 幂等键字符串格式统一为 `::`

**结论**：幂等键的字符串形式统一为
`{businessKey}::{session}::{stepNo}::{digest}`；由 `core/fingerprint.ts` 单点定义，
`governance/idempotency.ts` 只做校验与委托。

**理由**：代码里同时存在 `:` 与 `::` 两种拼法，其中一套还没人调用 ——
文档、实现、测试各说各话。统一后 aiwarden 的 `orderRef` 与文档口径一致。

**放弃了什么**：放弃了「不动线上字符串」的保守做法。新格式只是唯一键的编码，
不改变幂等维度，不影响历史数据的语义。

### 29. Oracle 加强后仍无缺陷，如实记录覆盖边界

**结论**：补齐 OTH2 / OTH8–10 与 CHS12–15 后做多 seed 扫描；扫描发现**先人工复核**，
确认不是 Oracle 误报才记作游戏缺陷；仍无缺陷则如实记录 seed 区间、步数与产物路径。

**理由**：裁决 18 已允许「未发现真实缺陷」，但要求如实记录扫描结论。
加强断言是为了让「未发现」更有说服力，不是为了让结论好看。

**放弃了什么**：放弃了「扫到一条就宣布发现 bug」的冲动 —— 误报会毁掉报告可信度。

## 第六部分：报告 v2 与收尾裁定（30–36）

### 30. 报告升级 v2，区分执行停止与游戏终局

报告 v2 保存公开初始状态、完整动作与前后状态、版本来源及停止原因；仅正常终局且必要检查完成才记 passed。旧 v1 不补造数据，新读取器明确拒绝。取代第 24 条对本轮语义变更仍保持 v1 的限制；幂等摘要算法不变。

### 31. 确定性约束区分基线与模型录制

基线由 seed、观察序号与显式上下文确定；模型不承诺相同 seed 重采样一致，缺陷复现使用录制动作且不重新调用模型。保留第 27 条的无状态 PRNG，扩展其适用边界。

### 32. 至少交付一个标明来源的预置缺陷闭环

补充第 18、29 条：不强求真实游戏缺陷，但必须用独立 HTTP 假服务完成发现、新会话复现和健康实现对照。预置错误必须标为 injected-fixture；健康前缀通过不能证明整局无缺陷。

### 33. 模型预算先于探索实验

取代第 16 条的预算暂缓决定。请求前预扣硬调用次数，usage 为软 token 停止线；未知用量不填零，恢复不得退还在途调用额度。检查点显式升版、写入失败停止请求，不将治理配额当量与模型 token 合账。

### 34. 治理许可与游戏副作用分别取证

只有明确 SUCCEEDED 的治理结果才允许执行或处理成功重放。治理与游戏不是原子事务；不明结果保留检查点，缺乏条件写保护时不自动补偿。报告公开快照与含凭证检查点分离，CI 仅上传脱敏产物。

### 35. 报告原因字段落闭合原因码，不落原文

`degradedReason` / `error` / `tokensUnavailableReason` / `governanceDegradedReason` 由自由文本改为闭合枚举（`DegradedReasonCode` / `StepErrorCode` / `TokenUnavailableReasonCode` / `GovernanceDegradedReasonCode`），Markdown 与 HTML 展示层映射为中文短句。安全不变量不变：原始错误文本与凭证一律不入报告。

兼容性：字段仍是可选字符串，历史报告中的旧文案在读取时统一收敛为 `unknown`，不拒绝旧文件；本项不升级报告版本（仍为 v2），因为结构未变、读取层已归一化。消费者不得依赖这些字段的展示文案，只允许依赖枚举值。

### 36. 收尾：MCP 通道与真实模型 60 步整局不做

- **MCP**：aiwarden 的治理面（幂等 / 配额 / 审计 / 补偿）已由 HTTP 客户端在同一套契约测试下覆盖。MCP 只替换传输层，不产生新的可验证证据，却要新增连接、鉴权、超时与 CI 依赖。
- **真实模型 60 步整局**：2026-11-06 已用 2 seeds × 10 步完成基线 / 模型同窗口对照（0 降级），链路、预算与报告均已验证。再跑整局只放大费用与随机波动，不改变任何结论。

影响面：PRD §14「后续 3」标为不做、§15 列入明确不做、§16 决策 6 收敛；README「待做」改为收尾裁定；ARCHITECTURE §4 / §5 / §6 同步。代码、契约与 CI 门槛均不变。
